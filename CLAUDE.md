# CLAUDE.md — ioBroker.fakeroku

Adapter-spezifischer Kontext. Globale Dev-Standards: `../CLAUDE.md` + `../CLAUDE_*.md`.

## Projekt

Roku-Emulator im LAN: ein ECP/SSDP-Controller (Logitech Harmony, Sofabaton) findet einen emulierten Roku und löst über Tastendrücke Ereignisse in ioBroker aus — die **Eingabe-Seite**, Gegenstück zum harmony-Adapter (Ausgabe). Greenfield-Neubau ab **v0.5.0** des community-`fakeroku` (Pmant 2017, Community-Wartung bis 0.4.0); Übernahme durch krobi. Feld-/Protokoll-Details: `../../Ressourcen/rokuemu/`.

## Architektur (`src/`)

- **`discovery/ssdp-responder.ts`** — handgebauter `dgram`-SSDP-Responder (Port 1900, Multicast 239.255.255.250). Empfang bindet 0.0.0.0:1900; Gruppen-Beitritt **pro Interface**: konkretes Interface → nur dieses + `setMulticastInterface` (NOTIFY-Egress gepinnt), Auto → **alle** routbaren IPv4 (Emulator-Familie/node-ssdp-Muster, damit Multi-Homed auf allen LANs gefunden wird). `onFatalError`-Callback meldet einen Socket-Tod zur Laufzeit an `main` (stoppt Announce, revidiert Zustand). ⚠️ `node-ssdp` taugt NICHT: hängt `::device` ans USN, ein echtes Roku sendet `uuid:roku:ecp:<uuid>` OHNE Suffix.
- **`ecp/ecp-http-server.ts`** — pro Gerät ein `node:http`-Server auf dem konfigurierten Port (Default 8060). Serviert UPnP-Description, `/query/device-info`, `/query/apps`; POST-Tasten → CommandEvent. **LAN-restringiert** (`lib/lan-guard.ts` `isLanClient`: private IPv4, Link-local, IPv6 link-/unique-local **und seit 1.4.0 eine global gültige IPv6-Adresse aus dem EIGENEN /64** — dieselbe Grenze gilt für SSDP-Suchen), sauberes 404 (nicht das alte leere 200). Malformierte `%`-Escapes in `Lit_`-Tasten bleiben roh (kein Wurf im Request-Handler), Steuerzeichen werden im Log ersetzt. Der POST-Body wird nicht gelesen — Node verwirft ihn beim Antwort-Ende selbst, ein `req.resume()` war doppelt (gemessen 2026-09-01, Test hält den Keep-alive-Vertrag). **Seit 1.5.0 protokolliert der Server erst NACH der Anwendung** (`onCommand` gibt zurück, ob der Befehl durchkam) — die Ratenbegrenzung deckt damit auch das Protokoll; der Befehlstext ist auf `MAX_LOGGED_DETAIL` (120) gedeckelt, die 403-Zeile auf eine je Minute. `onFatalError` meldet einen Server-Tod NACH dem Start an `main` (wie beim SSDP-Responder).
- **`ecp/device-info.ts`** — `SOFTWARE_VERSION` = **aktuelle Roku-Version** (der Pairing-Hebel — moderne Fernbedienungen prüfen sie; Stand 2026-09-03 erneut geprüft: weiterhin Roku OS 15.0 (15.10.2025), Quelle Wikipedia „Roku OS“ + Roku-Release-Notes; **bei jedem Release nachsehen**, ob ein neuer Major raus ist — die Schwelle der Sofabaton ist nirgends dokumentiert), Modell „Roku Ultra". `DEFAULT_APPS` (Netflix/YouTube/Prime/Disney+).
- **`ecp/ecp-command.ts`** — reiner Parser: POST-URL → CommandEvent; `COMMAND_TYPES` ist zugleich die Werteliste (`common.states`, nur Klartext-Strings) des Datenpunkts `commandType`.
- **`ecp/state-model.ts`** — `BASE_KEYS` (16) + `TV_KEYS` (11) = 27 feste Tasten, `commandToStateWrite`; der `command`-Text ist auf `MAX_COMMAND_LENGTH` (500) gedeckelt — die URL kontrolliert der Client bis ans Header-Limit.
- **`main.ts`** — Lifecycle. `onReady` (async, top-level try/catch): **pro Gerät eigenes try/catch** (ein belegter Port kippt die anderen nicht), dann **isolierter** SSDP-Start (Fehler = „Discovery aus", kein Total-Abbruch). **`info.connection` = VOLLSTÄNDIGKEIT** (seit 1.2.0: jeder konfigurierte Roku lauscht, nicht ≥1), NICHT an SSDP gekoppelt — ein übersprungenes Gerät ist eine Fehlkonfiguration, die der Nutzer beheben muss, und wäre sonst nur eine Protokollzeile. Nicht mitgezählt werden Konfig-Zeilen ohne brauchbaren Namen: die werden vorher stumm verworfen und hätten keinen Namen, den das Protokoll melden könnte. keydown-Watchdog (`HOLD_MAX_MS`) gegen hängende Hold-Tasten. **`onUnload` räumt Zeitgeber und Sockets synchron ab, meldet aber erst nach dem letzten Schreibvorgang fertig** (`.finally`, seit 1.2.0): `info.connection` ist der einzige Status dieses Adapters. **Live gemessen (2026-08-27): auf 1.1.0 kam der Schreibvorgang OHNE Warten trotzdem an** — ohne `stopInstance` endet der Prozess geordnet und leert seine offenen Schreibvorgänge noch. Das Warten schließt also ein Rennen, keinen beobachteten Defekt; auf einem langsamen oder ausgelasteten System ist der Ausgang sonst offen. Das Warten ist gefahrlos, weil das Manifest bewusst kein `supportedMessages.stopInstance` trägt (damit gewährt der Host die volle `stopTimeout`-Sekunde statt den Prozess sofort abzuschießen) — Mechanik: Memory `reference_stopinstance_verhindert_onunload`.
- **`lib/`** — reine Helfer: `sanitizeId`, `normalizeKey`, `deriveUuid` (md5 → stabile UUID) + **`resolveDeviceUuid`** (EINE Quelle für „welche Identität hat diese Konfigzeile" — Laufzeit UND Gerätemanager rufen sie, damit ein Edit nie eine andere Antwort speichert als die angekündigte), `i18n.ts` (`tName`/`tDesc`/`tRaw`), `detectPrimaryIPv4`/`detectLocalIPv4s` (Advertise-IP + Membership-Interfaces; die Advertise-Wahl überspringt seit 1.5.0 Docker-Standardbrücken) + **`ipv6Prefix64`/`listLocalIPv6Prefixes`** (die eigenen IPv6-Netzabschnitte für den LAN-Wächter), `lan-guard.ts` (`isLanClient`, Vertrauensgrenze beider Dienste), `errors.ts` (`errText` — EINE Stelle für „Message eines geworfenen Werts"), `constants.ts` (`DEFAULT_ECP_PORT` + **`RESERVED_IDS`/`OWN_INFO_IDS`** — eine Quelle für Dialog und Laufzeit), `logger.ts` (`AdapterLogger` = geteilter Logger-Typ). Hot-Path-Schreibvorgänge laufen über `writeState()` in `main.ts` (Rejection wird gefangen — ein `void setState` ohne `.catch` ist ein Absturz, sobald die States-DB beim Beenden schon zu ist).

## Design-Entscheidungen (belegt, nicht wieder aufmachen)

- **Datenmodell:** `<gerät>.command` (string, role `text`) = letzter Befehl; `<gerät>.commandType`; feste `<gerät>.keys.<Key>` (boolean, role **`sensor`** — NICHT `button.press`: repochecker **E1010** lehnt es ab). Alle Tasten **vorab** angelegt (kein lazy-Wachstum wie der Alte). Tastatur-`Lit_` + App-Starts landen NUR in `command` (kein Pro-Zeichen-Objekt-Wildwuchs).
- **Geräte-Identität überlebt das Umbenennen** (seit 1.4.0): eine Konfigzeile ohne gespeicherte `uuid` — die Manifest-Vorgabe, oder alles vor 0.8.0 — wird über `deriveUuid(name)` identifiziert. Ein Edit leitet deshalb aus dem **bisherigen** Namen ab (`resolveDeviceUuid(current)`), nie aus dem neuen: sonst wandert die SSDP-Identität bei einer bloßen Umbenennung und die gekoppelte Fernbedienung findet ihr Gerät nicht mehr (genau Bug A1 des Alt-Adapters). `main.ts` schreibt die abgeleitete `uuid` bewusst NICHT zurück — ein Schreibvorgang auf `native.*` startet den Adapter neu.
- **Tastenzustände werden beim START zurückgesetzt** (seit 1.4.0), nicht im `onUnload`: ein Impuls plant sein `false` 50 ms später, ein `keydown` hält bis zum `keyup`, und das Beenden wirft beide Zeitgeber weg, ohne zu schreiben. Nur der Start deckt auch Absturz und Abschuss ab; 27 Schreibvorgänge je Gerät im `onUnload` würden das `stopTimeout`-Budget aufbrauchen, das heute ein einziger bequem trägt. `setStateChanged` schreibt nur, wo der Wert abweicht — ein gesunder Baum kostet nichts. **Nicht** die 50-ms-Impulsüberlappung (die bleibt bewusst).
- **`info` ist ein reservierter Name — in BEIDEN Richtungen** (seit 1.4.0): der Dialog weist ihn ab, und `main.ts` überspringt so eine hand-eingetragene Zeile. Vorher machte sie aus dem eigenen Info-Kanal ein `device` und hängte `info.command`/`info.keys.*` darunter — ohne Warnung, und der Waisen-Durchgang übersprang `info` bedingungslos, die Reste blieben also für immer. Jetzt schützt er nur noch `info` + `info.connection` und räumt alles andere darunter weg.
- **Ein Update erreicht JEDEN Datenpunkt bestehender Anlagen** (krobi 2026-09-03, flottenweit): `refreshOwnObjects()` erneuert `info` + `info.connection` bei jedem Start per `extendObject`. js-controller legt `instanceObjects` nur an, wo sie FEHLEN — ohne den Aufruf erreicht ein geänderter Name nur Neuinstallationen, während Manifest und Gate grün aussehen. Derselbe Aufruf heilt den `info`-Typ nach dem Unfall oben. Namen/Beschreibungen aller Objekte kommen über `tName`/`tDesc`, Protokoll- und Nutzertexte (Tastenname, Gerätename) über `tRaw` — nie ein fester String. Konsistenz-Gate: `audit_instanceobjects_reach`.
- **Vertrauensgrenze IPv6: link-local, unique-local UND das eigene /64** (seit 1.4.0): an einem Anschluss mit nativem IPv6 trägt jedes Gerät im Haus eine global gültige Adresse aus dem Block des Anbieters — sie sieht aus wie eine Internetadresse. Nur das gemeinsame /64-Präfix unterscheidet „Fernseher im Wohnzimmer" von „Rechner im Internet". `lan-guard.ts` holt die eigenen Präfixe **faul und nur für so eine Adresse** (IPv4 und link-local kosten keinen Syscall) — und ist damit auch nach einem Präfix-Wechsel des Anbieters aktuell, statt beim Start eingefroren.
- **Der Waisen-Durchgang läuft an JEDEM Ausstieg von `onReady`** (seit 1.5.0): vorher lag er nur auf dem Erfolgspfad, also blieb der Baum des ZULETZT gelöschten Geräts für immer stehen — der Gerätemanager schreibt beim Löschen eine leere Liste, `onReady` kehrte davor um, und kein zweiter Pfad räumt je auf. Bedingung ist `Array.isArray(native.devices)` (`devicesKnown`): eine leere Liste heißt „der Nutzer hat alles gelöscht“ (aufräumen), ein fehlender Schlüssel heißt „nie konfiguriert / nicht lesbar“ (nichts anfassen, sonst tauscht man einen stehenden Baum gegen einen gelöschten). Auch der Ausstieg „keine routbare IPv4“ räumt auf — was in den Baum gehört, entscheidet die Konfiguration, nicht das Netz.
- **Die Advertise-Adresse ist nie eine Docker-Brücke, wenn es eine echte gibt** (seit 1.5.0): `pickPrimaryIPv4` nimmt die erste routbare IPv4, die NICHT in 172.17./172.18. liegt, und eine Brückenadresse nur als letzten Ausweg (im Container ist sie alles, was es gibt). Sonst trägt jede SSDP-Antwort eine Adresse, die keine Fernbedienung erreicht — bei grüner Instanz und einer Protokollzeile, die nach Erfolg aussieht. Dieselbe Lehre und dieselbe Regel wie hassemu v1.21.0 (dort live erlebt), damit die Flotte EINE Antwort gibt.
- **Ein sterbender ECP-Server widerruft `info.connection`** (seit 1.5.0): `EcpHttpServer` hat denselben `onFatalError`-Rückruf wie der SSDP-Responder — vorher wurde ein Server-Fehler NACH dem Start nur protokolliert, und die Instanz blieb grün vor einem Gerät, das nichts mehr beantwortet. Die Meldung nennt das Gerät; die anderen laufen weiter.
- **⚠️ Play≠Pause protokollbedingt UNGELÖST** — Harmony sendet für beide dieselbe `Play`-Taste (live belegt 2026-07-30).
- **⚠️ Apps über Harmony nicht steuerbar** — die Harmony-App-Tasten (Netflix …) senden NICHTS an den Adapter (aktivitäts-gebunden, kein lokaler ECP-`launch`). Der Parser KANN `launch:<id>` — nur Harmony liefert es nicht.
- **Port ist für die Funktion egal** — die Fernbedienung liest ihn aus der SSDP-Ankündigung. Default 8060 (echter Roku-Port, risikofrei). **Manuelles Feld** — Auto-Vergabe verworfen (krobi 2026-07-30).
- **Mehrere Rokus pro Instanz** (geteilter Port 1900), `singletonHost`.
- **Sentry** (seit 1.2.0) über `common.plugins.sentry` mit der geteilten power-dreams-Adresse — kein npm-Paket, kein Code; README-Abzeichen + `## Sentry`-Abschnitt sind gate-erzwungen. Kein `flush()` nötig: fakeroku läuft als Daemon, nicht im Zeitplan-Modus.
- **Vertrauensgrenze = LAN, beide Dienste** (seit 1.3.0; was „LAN" umfasst, ist seit 1.4.0 weiter gefasst — s. den IPv6-Punkt oben): ECP antwortet Nicht-LAN mit 403, SSDP ignoriert Nicht-LAN-Suchen (Reflection). Persistierte Geräte-IDs werden nur in der Form akzeptiert, die die Adapter je geschrieben haben (Hex / dashed uuid) — sie landen wörtlich in SSDP-Headern und XML. `native.devices` wird im Gerätemanager normalisiert (Expertenmodus/CLI können alles hinterlassen). **Ratenbegrenzung** (krobi-Ja 2026-09-01): `lib/rate-gate.ts` = Token-Bucket, **25 Befehle/s je emuliertem Roku**, Überschuss verworfen, Warnung höchstens 1×/min je Gerät — jeder angenommene Befehl kostet die States-DB 3+1 Schreibvorgänge, ein Flut-Gerät im LAN würde sonst den ganzen Host bremsen; SSDP-Suchen bleiben ungedeckelt (kein DB-Pfad).
- **Ein Symbol, überall dieselbe Datei** (seit 1.3.0): `admin/fakeroku.svg` in `io-package.json` (`icon`+`extIcon`) und im README-Kopf; `src/manifest.test.ts` hält das fest (bis 1.2.0 zeigte der Admin ein PNG aus der Pmant-Zeit, GitHub das SVG).

- **Zweige:** Arbeit auf `developing`, Release auf `master` — die CI prüft seit 2026-08-23 BEIDE (`push.branches`). Vorher lief sie nur auf dem Release-Zweig, wodurch ein nur unter Windows roter Test erst am Release-Tag auffiel (yamaha v1.1.0 verbrannt). `deploy` hängt am Tag, aus einem Push auf `developing` wird also nie ein Release.

## Befehle

- `npm run build` · `npm test` · `npm run lint` · `npm run release`.
- `npm run format` / `format:check` formatieren NUR Handgeschriebenes: die Ausnahmen stehen seit 1.5.0 **als Negativ-Muster im Skript** (`"!build/**" "!.github/**" "!io-package.json" "!README.md" "!CHANGELOG_OLD.md"`), wie bei nut2 und yamaha. ⚠️ **Keine `.prettierignore`** — der repochecker lehnt sie neben `prettier.config.mjs` + `@iobroker/eslint-config` ab (W0084 + W5048), deshalb führt sie kein Adapter der Flotte. Warum überhaupt Ausnahmen: `.github/` gehört den Bots der Community-Org, `io-package.json` und `README.md` schreibt das Release-Werkzeug in eigener Formatierung (sonst ist der nächste Release-Commit wieder „Drift"), `build/` ist erzeugt.
